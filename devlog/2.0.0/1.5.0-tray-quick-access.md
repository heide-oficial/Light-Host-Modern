# 1.5.0 development: tray Quick Access

Implemented Running and Installed menus in the host-owned tray popup.
Both left and right clicks open the popup. Each Running plugin appears once,
with its own submenu containing Open editor, bypass, duplicate, move up/down
and confirmed removal. Installed adds a new instance at the chain's end and opens its editor.
The main WinUI window does not need to be open.

The menu uses persistent instance/class identities, saved names and the existing
engine operations/version counters. It never uses a captured list index after
asynchronous menu lifetime. Removal resolves the ID again after confirmation.
Recovery protection and loading status are checked both at menu construction
and when applying a command. Created instances return their exact IDs so the
tray opens the new instance rather than guessing by position.

Installed sorts by display name and honors the saved manufacturer-grouping
preference. Search and sort choices that only live in an open WinUI window are
not copied. Lists longer than 30 entries use numbered ranges. Menu creation
reads metadata only; availability checks and plugin loading stay in the
existing engine action path. The themed popup is asynchronous, watches the
tray component lifetime and completes commands after menu teardown.

Existing minimized editors now restore when opened. Existing generic-editor
fallback and per-instance persistence remain in the common editor path.
Error/confirmation text is localized in English and Brazilian Portuguese.

Local application/build version identifiers are now 1.5.0; the changelog marks
this version as unreleased. No release, tag, commit or remote change is part of
this task. The existing README edit was left untouched.

Release compilation succeeded for the WinUI shell, native host, scanner and
update helper. All four executable file versions are 1.5.0. The current shell
was staged alongside the host under
`out/build/modern-validation/LightHostModern_artefacts/Release`. No portable ZIP
or installer was generated. WinUI reported the existing toolchain search-path
and packaging-capability warnings; the build completed successfully.

Follow-up: removed the duplicated Plugin actions list. Actions now live under
each Running plugin, starting with Open editor. The previous host executable
was in use, so the updated host is built into `out/build/tray-update` with the
current WinUI shell and scanner/update helper alongside it. The user's running
host was not stopped. Tests remain deferred.

Theme follow-up: the popup now uses a per-menu JUCE LookAndFeel rather than a
Windows HMENU with fixed system rendering. It reads Appearance/ThemeMode from
the same profile settings as WinUI on each opening; System uses JUCE's current
Windows app-theme detector. Windows high contrast overrides the normal palette.
Backgrounds, text, hover, checks, arrows and disabled text share the appearance
through all submenus. The LookAndFeel is retained through asynchronous menu
teardown and never replaces the global appearance used by plugin editors.
Physical screen coordinates are converted through JUCE's display mapping.
The theme follow-up compiled successfully in the canonical
`out/build/modern-validation/LightHostModern_artefacts/Release` folder after
rebuilding/staging WinUI. The running `out/build/tray-update` copy was left
untouched. No runtime or automated tests were run for this follow-up.

DPI/text-size follow-up: replaced fixed popup font/row sizing with a public
WinRT `UISettings.TextScaleFactor` query at each opening. COM initialization is
balanced and a failed query falls back to 100% text size. The hidden tray
component is placed at the clicked monitor and supplied as the popup target,
allowing JUCE to reconcile target/popup peer DPI without double scaling fonts.
Rows grow to fit the scaled font; JUCE measures widths and retains scrollable
menus for long lists. Detailed logs record both scale factors and row height.
See [Microsoft's text-scaling guidance](https://learn.microsoft.com/en-us/windows/apps/develop/input/text-scaling).
Runtime checks at multiple monitor scales and 100–225% text size remain deferred
under the request not to run tests.

Source review confirmed the DPI cause: `PopupMenu::createWindow` passes its
target HWND to JUCE's `ScopedThreadDPIAwarenessSetter`; without a target, the
Windows implementation temporarily switches an aware thread to DPI-unaware
mode. Supplying the real hidden tray component preserves its per-monitor
awareness during popup creation. The DPI/text-size change compiled successfully
to `out/build/tray-update/LightHostModern.exe`; the currently running canonical
build was not replaced or stopped. Its current WinUI payload and native helpers
were staged alongside the new executable.

Validation scope: compilation only, as requested. Automated tests and runtime/UI
validation were deliberately not run. Later validation should cover both tray
buttons, editors with the main window closed, minimized/generic editors, empty
and large lists, aliases, duplicate instances, language/grouping changes, menu
cancellation, stale selections, mutation during removal confirmation, read-only
recovery, failed loading, UI synchronization and shutdown with an open menu.
