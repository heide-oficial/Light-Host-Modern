# Named audio configuration contract

LightHostModern 2.0.0 uses IPC 5 for complete, generation-checked device selection. `select-audio-device` accepts one object with `backend`, `input`, `output`, binary channel masks `inputMask`/`outputMask` (up to 256 bits), `defaultInputChannels`/`defaultOutputChannels`, `sampleRate`, `bufferSize` and `expectedGeneration`. Zero rate/buffer requests the driver default. Empty input/output explicitly selects no audio device. The configured target and effective driver configuration remain distinct in `audioSelection` snapshots and operation results.

Before any driver access, the controller rejects stale generations and forbidden choices. It increments the generation once when accepting a manual configuration, suspending earlier recovery attempts. All masks and format values are applied together. Preferences are updated only after verifying the actual opened device. A failed attempt can restore the previous device only while it remains allowed; it never substitutes a similarly named device. An absent configured target survives fallback/recovery.

`attempted` records a manual request only while its generation is current. `editable` selects the effective configuration, then the current attempt, then the configured target. This lets the UI correct a rejected backend/device without saving the failed request as the configured preference. Device diagnostics continue to show `None` while no driver is open. A later generation invalidates that draft. Explicit `None` is persisted as suspended audio; the next host does not silently reopen it. Default channel selection may reuse saved masks only for the exact device pair; an explicit zero mask takes precedence.

`audio-device-options` returns the permitted names for a named backend without creating/opening a driver. `set-preferred-audio-device` accepts a generation plus named backend/input/output as one preference transaction. The preferred-device dialog edits a local draft, including after a backend change; cancelling it sends no mutation and saving it commits once. Legacy index methods are retained for synchronous native callers, while asynchronous UI selections use names and generation checks.

The legacy IPC setters `set-input-channel` and `set-output-channel` still accept `[channelIndex, enabled]` without a generation. The WinUI audio-intent path uses `select-audio-device` instead, so its queued channel edits carry the complete identity and expected generation.

## Enabled-device inventory

`enabled-audio-choices` returns `choiceToken`, backend names and enabled flags, device identities and enabled flags, and custom device names. Device identities use the original `backend|role|device` names; role is `input`, `output`, or the shared `device` role for ASIO. A displayed custom name never replaces that identity.

`update-enabled-audio-choices` accepts one object with `token` copied from `choiceToken` and three objects: `backends` maps original backend names to booleans, `devices` maps device identities to booleans, and `names` maps device identities to custom-name strings. An empty name restores the original display name. These objects may contain only the edited entries, but all three must be present.

The token covers the generation, inventory and enabled flags. The controller obtains a fresh inventory and validates the token, unique identities, flags and names before changing any preference. A stale token or invalid/ambiguous edit returns `device_list_changed` and applies none of the batch. Successful application invalidates the configuration once and closes the current device if it is now blocked. The IPC commands `set-enabled-audio-backend` and `set-enabled-audio-device` are rejected with `obsolete_device_command`; an old numeric position cannot target a different device after hotplug.

## Channel and mono intents

The UI queues audio edits against confirmed device identity, coalescing unsent absolute values within ordering barriers. Hardware channel changes use the complete generation-checked selection transaction. Enabling or disabling a pair changes both mask bits together. Switching hardware Individual/Pairs presentation alone is a local UI preference shared between Audio and the Chain hardware cards; it preserves enabled channels and stored connection endpoints and widths. Plugin/mixer port presentation is stored in the graph and likewise does not rewrite connections. Pending hardware channel selections cannot carry over to another device.

`set-mono-inputs` and `set-mono-output` each accept `{enabled, expectedGeneration}`. They preserve stream configuration, use the same device generation checks, and save separate preferences for the exact backend/input/output combination. `audioSelection.preferenceKey` lets the UI scope its local channel presentation to that same combination. `audioSelection.mainOutputPairActive` is true only when processing is available and both physical principal outputs are active. See [Audio processing](audio-processing.md) for mono mixing and [Persistence and recovery](persistence-and-recovery.md) for defaults and storage.
