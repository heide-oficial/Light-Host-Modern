# Update and local package contract

This document describes the 2.0.0 implementation; the [release validation record](release-2.0.0-validation.md) identifies which package revisions and update paths were actually exercised.

## Discovery and eligibility

The native host owns a background release check while **New release notifications on Windows** is enabled. It runs at startup and every six hours independently of the WinUI window, with a five-minute retry after transport failures. A cancellable worker requests only the fixed repository's latest-release endpoint over HTTPS, rejects redirects, limits the response to 4 MiB and applies a 20-second request deadline. Only newer, stable, non-draft releases with the matching canonical GitHub URL qualify. This check never downloads an installation package or touches the audio callback.

Host and UI requests share one Windows-notification delivery path and normalized version history for the current host session. Preferences are checked again at delivery. Restarting the host clears that history; reopening the UI does not. Disabling Windows notifications cancels pending background work. In test profiles, the host's background checker uses only an explicit local `Temp/background-release-fixture.json` and does not post a real Windows notice. Without that fixture, it does not fetch release metadata. This restriction applies to the host background checker, not every UI update request.

The UI has its own latest-release request and candidate validation. Its isolated test fixture is `Temp/update-fixture.json`; without that file, `UpdateService::checkAsync` uses the GitHub endpoint even for a test profile. A UI update test that must stay offline therefore needs the fixture and its local package/manifest files.

A candidate contains a three-part numeric version (with an optional leading `v` or `V`), x64 architecture, distribution (`installed` or `portable`), exact artifact name, canonical HTTPS release/download URLs, expected byte count and SHA-256. Version components are limited to 0–65535 and reject leading zeroes or prerelease suffixes. Packages must be larger than zero and no larger than 2 GiB. The updater accepts only `LightHostModern-<version>-Setup.msi` and `LightHostModern-v<version>-Portable.zip`; for 2.0.0, these are `LightHostModern-2.0.0-Setup.msi` and `LightHostModern-v2.0.0-Portable.zip`. Unversioned aliases are neither published nor accepted as update candidates. Installation registration must match the actual host executable location, not merely an unrelated installed copy.

Valid GitHub release metadata alone does not enable an internal update. The UI also requires a trusted signature over `update-manifest.json`, matching artifact size and digest, and a supported installation layout. Failure of those checks leaves the release available for browser download but clears the internal-update candidate. Portable application additionally requires the versioned launcher layout and NTFS.

## Download and shutdown

Each download owns a unique directory below the profile temporary directory. Transfer uses a fixed 256 KiB buffer, incremental SHA-256, byte progress and cooperative cancellation with bounded network timeouts. Only a complete, flushed file with the expected size and digest can be renamed from `.partial`. Cancellation or failure removes only that operation's package files. Package inspection also verifies internal version, architecture and application identity. ZIP validation checks required executables and the release manifest without extraction; MSI validation reads its database without starting installation.

Update operations live under `Temp/Updates` beside the UI preferences, or under the isolated profile's `Temp/Updates`. Cache maintenance recognizes only operation directories with its own marker and rejects reparse paths. It preserves active UI/helper leases and up to three recent operations younger than seven days; eligible older or excess operations can be removed. Other temporary directories and user profiles are not cache-cleanup targets.

Settings offers **Update in app**, **Download from GitHub**, and **Cancel**. The browser option opens the matching release asset, or the release page when direct-update metadata is unavailable. No update starts without an explicit choice. Audio continues during download and preparation; applying the update stops processing while installation takes place, then reopens the application with the same profile.

Before applying either distribution, the UI asks the host to `flush-session`. A helper copied outside the application directory validates and holds the package against modification, opens handles to the exact host/UI process instances, and acknowledges readiness. The UI then arms the helper, requests host shutdown and exits. Arming comes first because the host also closes its UI during shutdown; normal window cleanup must not cancel a committed update. Both processes must exit and the helper must be armed before replacing files. Cancellation, missing acknowledgement, process identity mismatch or the helper's two-minute shutdown deadline aborts application. This apply helper never kills the running host or UI to complete an update.

## Versioned portable application

Portable distributions have a stable `LightHostModern.exe` launcher at the root and complete payloads under `versions/<version>-<inventory-hash>/`. `portable-layout.json` identifies the initially extracted payload. Normal updates never overwrite the root launcher or the active payload. Old flat portables require one manual extraction of the new distribution; preferences remain in the existing user profile.

Preparation extracts only an allowlisted, complete candidate to a unique staging directory. Paths reject traversal, reserved names, streams and reparse points. `payload-manifest.json` lists every payload file with size and SHA-256, including `legacy-payload-files.json`. Both missing and unexpected files fail validation. The complete candidate moves into `versions` before activation; activation changes only the durable selection records.

Native payload I/O and durable descriptor replacement use normalized absolute extended Windows paths. This prevents staging plus WinUI asset names from exceeding the legacy 260-character limit without changing a machine-wide registry setting. Path validation still runs before opening files, including reparse-point checks on existing parents; attribute errors other than a missing path are rejected. See Microsoft's [maximum path length contract](https://learn.microsoft.com/en-us/windows/win32/fileio/maximum-file-path-limitation). Regression tests cover payload hashing and metadata replacement beyond 280 characters, plus prepare/apply/rollback of the actual release ZIP.

`portable-state-0.json` and `portable-state-1.json` contain checksummed, sequenced descriptors for confirmed, previous and candidate versions. Temporary files are flushed and replaced with write-through. The launcher validates descriptors and payloads before launch, records a candidate attempt, then waits up to 15 seconds for a per-launch ready event. The host signals readiness before restoring user plugins. If the newly launched process times out, the launcher terminates that startup attempt; a failed candidate can fall back to the confirmed payload in the same launch. An interrupted candidate attempt is recovered on a subsequent launch rather than retried indefinitely. A user plugin failing after readiness does not roll back the application. Retention preserves the initial payload, confirmed/previous/candidate references and payloads leased by a running host. Power-loss and file-system durability still require the disposable-VM validation matrix.

## Manifest trust and release signing

Every internally applied package also needs a bounded RSA/SHA-256 signed release manifest, containing version, architecture, minimum launcher version, artifact names/sizes/digests and the portable inventory digest. Trust roots are reviewed public keys compiled into `Source/UpdateTrustKeys.h`; downloaded metadata cannot supply its own trusted key. Normal updates reject downgrades; local recovery may return to an explicitly retained previously confirmed payload. Multiple embedded keys permit rotation. The root launcher itself requires a separate manual migration when its contract changes.

The development tree embeds the maintainer's public RSA-3072 update key, provisioned on 2026-10-02. Its key ID is `f8f68adf39be2eb93d3e2658c0896c7203d51b495989430ead19e6171149d700`. Only the public key is committed. The private key is held in the maintainer's `CurrentUser\My` Windows certificate store and permits encrypted recovery export, not plaintext private-key export. This pin authenticates update manifests inside LightHostModern; it is not an Authenticode identity trusted by Windows.

`Utilities/Initialize Update Signing.ps1` bootstraps an empty trust header or verifies the existing dedicated identity. It must not be used to rotate an established key silently. `Utilities/Update Signing.ps1` signs using the certificate store without exporting private material. `LIGHTHOST_MANIFEST_SIGNING_THUMBPRINT` selects that certificate; release builds also read its persistent user setting when the current shell predates setup. The release script checks that the public key is embedded before building and validates the final manifest with the rebuilt helper. Publish `update-manifest.json` and `update-manifest.sig` alongside the exact packages whose hashes they contain.

The maintainer confirmed an encrypted private-key backup on 2026-10-02. `Utilities/Backup Update Signing Key.ps1` asks for the password interactively; never put that password, a PFX, or private key in the repository, logs, release assets or chat. Keep the recovery password separately from the backup. Do not discard the original key during reinstall/migration. The certificate expiry is not a network trust mechanism: the updater validates the embedded public key directly.

Clients distributed with an empty trust list need a manual bootstrap installation. The stable portable launcher also embeds trust and is not replaced during ordinary payload updates. Consequently, publishing a payload with a new key does not update old launchers: future rotation requires a compatible launcher migration or a key provisioned in that launcher in advance. Installed clients likewise need a signed transition before a new key is used. Authenticode and SignPath onboarding remain separate publication work; configuring this public key alone does not certify that full update lifecycle validation has passed.

## Installed application and validation

Installed updates run Windows Installer with `/quiet /norestart`, requesting elevation through Windows when needed. This preserves installation registration, repair and uninstall support; it is not a raw replacement of MSI-managed files. Outcomes and logs distinguish cancellation, failure, success and restart-required results. The app reopens after the operation when its files are usable. Isolated test profiles may exercise portable application and preserve their profile arguments across restart, but cannot launch MSI installation.

The normal release workflow uses one canonical WinUI output directory, builds host/UI/scanner/plugin worker/helper/launcher, runs CTest, verifies payload contents and produces local MSI/ZIP plus SHA-256/size metadata. `-SkipBuild` and `-SkipTests` reuse outputs and omit CTest respectively; records from such a run must not claim a new compilation or test pass. Manifest signing is conditional on its configured certificate. Package inspection reads and validates packages without installing them; actual installation, upgrade, repair and removal require a disposable Windows environment. See [Build and release](build-and-release.md).

## Rename compatibility

Release package names are versioned; older updaters that depend on an unversioned alias need a manual download from the release page. Installation compatibility is separate: the MSI ProductName remains `Light Host Modern`, its UpgradeCode remains unchanged, and small legacy executables forward to the canonical app. The visible app, shortcuts, install folder and main executable use `LightHostModern`.

Package validation retains exact names, repository URLs, versions, architectures, sizes and digests. Creating local packages or editing this contract does not publish a release.
